# 模块2项目介绍与模块3对接

## 1. 文档目的

本文说明“知识库构建与索引模块（模块2）”当前的完成情况、项目结构、运行方式、输出文件，并明确“查询理解与混合检索模块（模块3）”应使用哪些模块2产物。

## 2. 模块2完成情况评估

### 2.1 已完成能力

- 读取模块1输出的制度正文 `parsed_docs.jsonl`。
- 读取模块1输出的表格证据 `table_evidence.jsonl`。
- 生成制度条款 chunk：`clause_chunks.jsonl`。

- 使用本地 embedding 模型 `Model/bge-small-zh-v1.5` 生成全量 chunk 向量。

- 建立 FAISS 向量索引 `faiss.index`。
- 保存 FAISS 向量序号与 chunk ID 的映射 `chunk_id_map.json`。

- 提供统一检索接口：

  - `hybrid_search()`：BM25 + FAISS 混合检索

## 4. 模块2输入说明

模块2的输入来自模块1，正式输入只有两个文件：

| 模块1产物 | 模块2用途 | 是否必需 |
|---|---|---|
| `data/parsed/docs/parsed_docs.jsonl` | 生成制度条款 chunk | 是 |
| `data/parsed/tables/table_evidence.jsonl` | 生成表格证据 chunk | 是 |

模块2默认不读取：

| 文件 | 原因 |
|---|---|
| `data/parsed/tables/parsed_tables.jsonl` | 这是完整单元格审计归档，约百万级记录，不适合作为默认建库输入。 |
| `data/parsed/meta/doc_meta.jsonl` | 当前建库所需元数据已经嵌入 `parsed_docs.jsonl` 和 `table_evidence.jsonl`。 |
| 模块1 MySQL | 模块间交付使用 JSONL 快照，模块2不直接依赖模块1数据库。 |

## 5. 模块2输出文件说明

模块2输出分为两类：

- 知识库数据文件：保存在 `data/processed/kb_rebuild/`
- 检索索引文件：保存在 `indexes/kb_rebuild/`

### 5.1 知识库数据文件

```text
data/processed/kb_rebuild/
├─ clause_chunks.jsonl
├─ table_chunks.jsonl
└─ metadata.db
```

| 文件 | 作用 | 模块3是否直接使用 |
|---|---|---|
| `clause_chunks.jsonl` | 条款 chunk 明细。每行是一条制度/监管正文证据，保留正文、标题、章节、条款号、来源等信息。 | 一般不直接使用，主要用于审计、检查和重建索引。 |
| `table_chunks.jsonl` | 表格 chunk 明细。每行是一条表摘要或行级表格证据，保留指标、期间、单位、单元格范围和值。 | 一般不直接使用，主要用于审计、检查和重建索引。 |
| `metadata.db` | SQLite 数据库，保存所有 chunk 的完整文本、来源和元数据；同时包含 SQLite FTS5/BM25 检索表。 | 需要，是模块3查回完整证据的核心文件。 |

### 5.2 检索索引文件

```text
indexes/kb_rebuild/
├─ bm25_corpus.jsonl
├─ embeddings.npy
├─ faiss.index
├─ chunk_id_map.json
└─ vector_meta.json
```

| 文件 | 作用 | 模块3是否直接使用 |
|---|---|---|
| `bm25_corpus.jsonl` | BM25 关键词检索语料备份，记录 `chunk_id`、`chunk_type`、`doc_id` 和检索文本。 | 一般不直接使用，BM25 在线检索主要走 `metadata.db` 中的 FTS5 表。 |
| `embeddings.npy` | 全量 chunk 的 embedding 向量矩阵，形状约为 `125166 × 512`。 | 一般不直接使用，主要用于调试、复查或重建索引。 |
| `faiss.index` | FAISS 向量索引，用于根据用户问题做语义相似度检索。 | 需要，是向量检索核心文件。 |
| `chunk_id_map.json` | 保存 FAISS 内部向量序号与业务 `chunk_id` 的对应关系。 | 需要，向量检索命中后靠它映射回具体 chunk。 |
| `vector_meta.json` | 保存模型名、向量维度、chunk 数量、相似度类型、源文件路径等索引元信息。 | 需要，用于确认模型和索引配置是否匹配。 |

## 6. 模块3应该使用哪些文件

模块3正式运行时，核心使用以下 4 个文件：

```text
data/processed/kb_rebuild/metadata.db
indexes/kb_rebuild/faiss.index
indexes/kb_rebuild/chunk_id_map.json
indexes/kb_rebuild/vector_meta.json
```

可以这样理解：

| 文件 | 模块3用途 |
|---|---|
| `metadata.db` | 根据 `chunk_id` 查回完整证据文本、来源和元数据；也可直接做 BM25 检索。 |
| `faiss.index` | 根据问题 embedding 查找语义相似 chunk。 |
| `chunk_id_map.json` | 把 FAISS 返回的向量序号转换成 `chunk_id`。 |
| `vector_meta.json` | 确认向量模型、维度和 chunk 数量，避免索引与模型不匹配。 |

模块3通常不需要直接读取：

```text
data/processed/kb_rebuild/clause_chunks.jsonl
data/processed/kb_rebuild/table_chunks.jsonl
indexes/kb_rebuild/bm25_corpus.jsonl
indexes/kb_rebuild/embeddings.npy
```

这些文件主要用于模块2重建、调试、审计和答辩说明。

## 7. 模块3是否需要使用模块2的模型

结论：如果模块3在本地直接调用模块2的向量检索或混合检索接口，就需要使用同一个 embedding 模型。

当前模型路径为：

```text
Model/bge-small-zh-v1.5/
```

原因是：

```text
faiss.index 里面保存的是“知识库 chunk 的向量”
用户问题进入系统后，也必须先被同一个模型转成“问题向量”
然后才能在 FAISS 里做相似度搜索
```

因此：

| 场景 | 模块3是否需要模型 |
|---|---|
| 模块3直接调用 `reader.vector_search()` | 需要 |
| 模块3直接调用 `reader.hybrid_search()` | 需要 |
| 模块3只调用 `reader.search()` 做 BM25 | 不需要 |
| 模块2以后封装成独立后端 API，模块3只请求 API | 模块3本地不需要，但运行 API 的后端需要 |

当前项目采用“模块3直接调用模块2本地接口”的方式，因此模块3成员电脑上也应具备：

```text
Model/bge-small-zh-v1.5/
```

或者确保团队共享的后端服务所在机器有这个模型目录。

注意：模型文件通常较大，不建议提交 Git。`.gitignore` 已经忽略 `Model/` 下的模型权重。团队协作时可以通过网盘、压缩包或共享盘传给模块3成员，放回同一路径即可。

### 8.2 三种检索方式

#### BM25 关键词检索

适合精确词、文号、指标名完全匹配的问题：

```python
results = reader.search("资本充足率", top_k=5)
```

#### FAISS 向量检索

适合表达不完全一致、需要语义召回的问题：

```python
results = reader.vector_search("银行资本监管要求", top_k=5)
```

#### BM25 + FAISS 混合检索

推荐模块3优先使用。它同时利用关键词召回和语义召回：

```python
results = reader.hybrid_search("商业银行资本充足率有什么要求", top_k=5)
```

## 11. 模块2与模块3职责边界

模块2负责把知识库建好，模块3负责根据用户问题决定怎么查。

| 模块 | 负责内容 |
|---|---|
| 模块2 | chunk 切分、元数据挂载、SQLite/BM25、embedding、FAISS、基础向量/混合检索接口。 |
| 模块3 | 查询理解、问题类型判断、关键词/指标/年份/机构抽取、候选合并、业务过滤、最终 rerank，输出 Top 证据包给模块4。 |
| 模块4 | 根据模块3返回的证据生成答案，做数字校验、引用溯源和拒答。 |

注意：模块2提供的 `hybrid_search()` 是“基础混合检索能力”，不是模块3的全部工作。模块3仍然需要在此基础上做更细的查询理解、条件过滤和最终排序。

一句话区分：

```text
模块2：把资料整理成可查的知识库。
模块3：看懂用户问题，并从知识库里找最合适的证据。
模块4：根据证据生成可信答案。
```

## 14. 当前限制与后续建议

- 当前向量索引为本地 CPU 构建，耗时较长；后续若有 GPU，可显著加快 embedding 构建速度。
- 当前基础 rerank 属于模块2提供的轻量排序，不替代模块3的最终业务排序。
- 表格 chunk 数量较多，模块3做问题理解时应尽量抽取年份、指标、机构等条件，以减少候选噪声。
- 大文件路径必须统一，尤其是 `kb_rebuild`，不要再使用旧的样本路径 `data/processed/` 根目录。
- 若模块1重新解析并导出新数据，模块2必须重新执行 `build_kb.py` 和 `build_vector_index.py`，否则 `metadata.db` 与 `faiss.index` 可能不一致。

## 15. 最终判断

模块2已经完成当前阶段要求，可以向模块3交付。

模块3正式需要关注的模块2产物是：

1. `data/processed/kb_rebuild/metadata.db`
2. `indexes/kb_rebuild/faiss.index`
3. `indexes/kb_rebuild/chunk_id_map.json`
4. `indexes/kb_rebuild/vector_meta.json`
5. `Model/bge-small-zh-v1.5/`

其中前 4 个是模块2知识库与索引产物，第 5 个是向量检索运行时需要的本地 embedding 模型。

模块3不需要重新读取模块1输入文件，不需要重新切 chunk，也不需要重新构建 FAISS。模块3只需要基于模块2接口做查询理解、条件过滤、候选合并和最终证据排序。
