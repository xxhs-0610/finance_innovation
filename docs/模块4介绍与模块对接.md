# 模块4：答案生成与可信控制

## 1. 模块定位

模块4位于在线问答链路的核心位置，负责把模块3检索到的证据转换为可核验、可追溯的结构化答案。

完整链路如下：

```text
用户问题
   ↓
模块3：查询理解与混合检索
   ↓ Top-K 证据包
模块4：答案生成与可信控制
   ↓ 结构化回答
模块5：后端 API 与前端展示
```

普通问答系统通常直接让大模型生成答案，而本项目要求模型只能根据给定证据回答。答案生成完成后，还需要检查数字、日期、文号、机构名称和规范性用语。当证据不足或生成内容无法被证据支持时，系统会主动拒答，避免输出未经核验的信息。

一句话概括模块4的作用：

> 模块3负责找到证据，模块4负责把证据变成可信答案。

## 2. 主要职责

模块4主要负责以下工作：

1. 统一模块3返回的证据格式。
2. 为证据分配 `E1`、`E2` 等引用编号。
3. 构造只能基于证据回答的生成提示词。
4. 根据证据生成答案，并在答案中标明引用来源。
5. 校验答案中的数字、比例、日期、文号和机构名称。
6. 校验“应当、不得、可以、原则上”等规范性表达。
7. 判断证据是否足够、是否与问题相关。
8. 在证据不足或校验失败时触发拒答。
9. 输出置信度、风险提示和校验明细。

## 3. 当前已经完成的内容

### 3.1 结构化回答格式

已经在 `app/schemas/answer_schema.py` 中实现统一回答结构，主要字段包括：

| 字段 | 说明 |
|---|---|
| `status` | 回答状态，当前为 `answered` 或 `refused` |
| `answer` | 最终答案正文 |
| `evidence` | 本次回答使用的证据列表 |
| `citations` | 答案引用的证据编号，例如 `E1` |
| `confidence` | 取值范围为 0 到 1 的置信度 |
| `risk_tips` | 适用范围、证据不足等风险提示 |
| `verification` | 数字、日期、文号、机构名等校验结果 |
| `refusal_reason` | 拒答原因，仅拒答时出现 |

该结构保留了现有前端已经使用的 `status`、`answer`、`evidence` 和 `risk_tips` 字段，因此不会破坏模块5当前的调用方式。

### 3.2 证据标准化与引用

已经实现模块3证据包的标准化处理：

1. 支持接收字典或带 `to_dict()` 方法的检索结果。
2. 清理没有正文内容的无效证据。
3. 保留原始 `source` 和 `metadata` 信息。
4. 自动为证据分配 `E1`、`E2`、`E3` 等编号。
5. 保留 `doc_id`、条款号、表名、sheet 和单元格位置等回溯字段。

### 3.3 证据约束生成

已经在 `app/generation/answer_generator.py` 中完成统一生成入口：

```python
from app.generation.answer_generator import generate_answer

result = generate_answer(question, evidence)
```

当前默认使用保守的抽取式生成方式，直接从检索证据中组织答案，并在每条结论后添加 `[E1]` 形式的引用。

这种方式不依赖外部大模型 API，因此当前仓库安装完成后即可测试和联调。后续团队确定具体大模型后，可以通过下面的方式注入模型生成函数：

```python
result = generate_answer(
    question,
    evidence,
    generator=my_llm_generator,
)
```

无论使用默认生成器还是外部大模型，最终答案都会进入可信校验流程。

### 3.4 Evidence-aware Prompt

已经在 `app/generation/prompt_builder.py` 中实现证据约束提示词，核心要求包括：

1. 只能使用给定证据回答。
2. 不得增加证据中没有的事实和数字。
3. 每个结论必须引用证据编号。
4. 证据不足或冲突时不得猜测。
5. 优先输出结论，再说明依据和风险。

该提示词可供后续接入本地模型或云端大模型时直接使用。

### 3.5 关键字段校验

已经在 `app/generation/verifier.py` 中实现确定性校验，当前可以检查：

1. 金额和普通数值。
2. 百分比和监管阈值。
3. 日期和统计期间。
4. 监管政策文号。
5. 监管机构和金融机构名称。
6. “应当、必须、不得、禁止、可以、原则上”等规范性用语。
7. 答案是否包含证据引用。
8. 答案是否引用了不存在的证据编号。

例如，证据中规定资本充足率不得低于 `8%`，如果生成器回答为 `10%`，校验器会把 `10%` 标记为无法由证据支持，并拒绝输出该结论。

### 3.6 拒答机制

已经在 `app/generation/refusal.py` 中实现以下拒答条件：

1. 用户问题为空或缺少可识别关键词。
2. 模块3没有返回可用证据。
3. 证据与问题明显不相关。
4. 证据缺少 `source.doc_id`，无法追溯原文。
5. 生成答案包含证据外的关键字段。
6. 答案没有提供证据引用。
7. 答案引用了不存在的证据编号。
8. 外部答案生成服务调用失败。

拒答时系统会返回明确原因，而不是继续猜测答案。

### 3.7 元数据问题回答

当前默认生成器已经支持直接回答以下类型的问题：

1. 文件由哪个机构发布。
2. 文件的发布日期是什么。
3. 文件标题是什么。
4. 原文链接是什么。

这些答案直接来自证据的 `source` 字段，并同样经过引用和关键字段校验。

### 3.8 测试情况

已经新增 `tests/test_module4_generation.py`，覆盖以下场景：

1. 正常生成带引用的答案。
2. 无证据时拒答。
3. 不相关证据拒答。
4. 生成器虚构数字时拒答。
5. 文号和机构名称校验。
6. 多证据引用。
7. 列表序号不会被误判为业务数字。
8. 外部生成服务异常时安全拒答。
9. 发布机构和发布日期问题。
10. Evidence-aware Prompt 格式。

目前仓库全部 14 项自动化测试已经通过，其中包括原有模块1、模块2测试和新增模块4测试。

此外，已经使用模块2临时知识库完成端到端验证：

```text
模块2构建知识库
   ↓
模块3返回 SearchResult 证据
   ↓
模块4生成答案
   ↓
返回 answered、引用、置信度和校验结果
```

## 4. 与模块3的对接

模块3是模块4的直接上游，负责问题理解、知识库检索和证据排序。

### 4.1 模块3需要提供什么

模块3需要向模块4提供用户问题和 Top-K 证据列表。每条证据至少需要包含：

```json
{
  "chunk_id": "doc001_clause_0001",
  "chunk_type": "clause",
  "score": 1.0,
  "text": "商业银行资本充足率不得低于8%。",
  "source": {
    "doc_id": "doc001",
    "title": "商业银行资本管理办法",
    "issuer": "国家金融监督管理总局",
    "publish_date": "2023-11-01",
    "clause_no": "第十条",
    "source_url": "https://example.com/doc001"
  },
  "metadata": {}
}
```

表格证据还应尽量保留：

1. `sheet_name`
2. `table_name`
3. `cell_ref`
4. `metric_name`
5. `period`
6. `unit`
7. `value` 或 `values`

### 4.2 与模块3联调时的检查点

1. Top-K 证据是否真的能够回答问题。
2. 证据是否按照相关性正确排序。
3. 条款证据是否保留条款编号。
4. 表格证据是否保留期间、单位和单元格位置。
5. 每条证据是否包含可追溯的 `doc_id`。
6. 证据内容是否过长、重复或互相冲突。

### 4.3 当前对接状态

当前模块3的 `retrieve_evidence()` 会返回模块2的 `SearchResult.to_dict()` 结果，该结构已经能够被模块4直接接收。

因此，模块3到模块4的数据结构已经打通。后续模块3完善混合检索和 rerank 时，只要保持现有证据字段不变，模块4不需要修改调用方式。

## 5. 与模块5的对接

模块5是模块4的直接下游，负责 FastAPI、前端展示和完整系统编排。

### 5.1 模块4输出给模块5的内容

正常回答示例：

```json
{
  "status": "answered",
  "answer": "商业银行资本充足率不得低于8%。[E1]",
  "evidence": [],
  "citations": ["E1"],
  "confidence": 0.9,
  "risk_tips": [],
  "verification": {
    "passed": true,
    "issues": [],
    "unsupported_claims": []
  }
}
```

拒答示例：

```json
{
  "status": "refused",
  "answer": "当前证据不足以支持确定性回答，请补充问题条件或检查知识库范围。",
  "evidence": [],
  "citations": [],
  "confidence": 0.0,
  "risk_tips": ["没有可用证据。"],
  "refusal_reason": "没有可用证据。"
}
```

### 5.2 模块5需要展示什么

前端建议展示：

1. 答案状态。
2. 最终答案。
3. 置信度。
4. 证据编号和证据正文。
5. 文档标题、条款号或表格位置。
6. 风险提示。
7. 拒答原因。
8. 原文链接或本地文件位置。

### 5.3 当前对接状态

当前 `app/api/main.py` 已经使用下面的链路：

```python
evidence = retrieve_evidence(question)
return generate_answer(question, evidence)
```

因此模块4已经接入现有 API 调用入口。当前 Streamlit 前端也能够继续读取 `status`、`answer`、`evidence` 和 `risk_tips`。

模块5后续可以继续增加置信度、引用编号和校验详情的可视化，但不需要修改模块4的核心接口。

## 6. 与模块6的关系

模块6不是模块4的直接运行依赖，但需要使用模块4的结构化结果开展评测。

模块4可以向模块6提供以下指标数据：

1. 回答成功率。
2. 拒答率和拒答准确率。
3. 关键字段错误率。
4. 证据引用正确率。
5. 未支持声明数量。
6. 置信度分布。
7. 平均生成和校验时间。

模块6可以直接读取 `status`、`confidence` 和 `verification` 字段完成自动统计。

## 7. 当前尚未完成的内容

模块4目前已经具备可运行的可信回答闭环，但以下工作需要在后续联调阶段继续完成：

1. 根据团队最终选择接入具体的大模型 API 或本地模型。
2. 为模型调用增加超时、重试和调用耗时统计。
3. 使用正式评测集调整证据相关性阈值和置信度计算方式。
4. 增强对复杂语义冲突和跨文档推理的校验能力。
5. 与模块5共同完善置信度、引用和校验详情的前端展示。
6. 与模块6共同确定拒答准确率和关键字段错误率的评分规则。

其中，具体大模型尚未接入不是当前代码错误。仓库目前没有规定统一的模型供应商、模型名称和密钥环境变量，因此当前实现采用可离线运行的默认生成器，同时保留统一的模型注入接口。

## 9. 总结

模块4当前已经完成从“证据包”到“可信结构化答案”的基本闭环：

```text
证据标准化
   ↓
证据约束生成
   ↓
数字和关键字段校验
   ↓
通过校验则正常回答
   ↓
校验失败或证据不足则拒答
```

需要直接对接的成员是：

1. **3号模块负责人**：向模块4提供稳定的 Top-K 证据包。
2. **5号模块负责人**：接收并展示模块4的结构化回答。

还需要配合的成员是：

3. **6号模块负责人**：使用模块4输出完成可信度、拒答率和关键字段错误率评测。
