# 模块4项目介绍与后续模块对接

## 1. 模块概述

模块4是“答案生成与可信控制”模块，位于模块3检索和模块5系统展示之间，负责把模块3返回的证据包转换成可验证、可追溯、可安全展示的结构化回答。

完整在线问答链路如下：

```text
用户问题
   ↓
模块3：查询理解、混合检索与证据筛选
   ↓ RetrievalResponse / Top-K 证据
模块4：证据约束生成、关键字段校验、拒答与澄清
   ↓ 结构化 AnswerResult
模块5：API 封装与前端展示
   ↓
最终问答页面

模块4结构化结果
   ↓
模块6：答案准确率、引用正确率、拒答率等评测
```

模块4不负责重新解析原始文件，也不负责重建知识库和向量索引。它的核心任务是保证最终回答只来源于模块3提供的可靠证据，并在输出前完成关键字段校验。

一句话概括模块4的作用：

> 模块3负责找到证据，模块4负责把证据转换成可信答案，并阻止未经证据支持的内容输出。

## 2. 模块职责

模块4主要负责以下五类工作：

1. 证据约束生成。
2. 数字和关键字段校验。
3. 规范性表达校验。
4. 证据不足时拒答或请求澄清。
5. 向后续模块输出统一结构化结果。

具体任务包括：

- 统一模块3返回的证据格式。
- 为每条证据分配 `E1`、`E2` 等引用编号。
- 构造 Evidence-aware Prompt。
- 强制答案引用证据编号。
- 校验金额、比例、日期、文号和机构名称。
- 校验“应当、必须、不得、禁止、可以、原则上”等规范性表达。
- 判断证据是否充分、是否与问题相关、是否可以追溯到原始文件。
- 处理模块3返回的正常回答、检索降级、需要澄清和无证据状态。
- 输出答案、证据、引用、风险提示、置信度和校验详情。

## 3. 模块文件组成

| 文件 | 作用 |
|---|---|
| `app/generation/prompt_builder.py` | 构造只允许基于证据回答的 Evidence-aware Prompt。 |
| `app/generation/answer_generator.py` | 模块4统一入口，负责状态处理、答案生成、引用、风险提示和置信度。 |
| `app/generation/verifier.py` | 校验数字、比例、日期、文号、机构名、规范词和证据引用。 |
| `app/generation/refusal.py` | 判断证据充分性，生成统一拒答结果。 |
| `app/schemas/answer_schema.py` | 定义模块4交付给后续模块的结构化回答格式。 |
| `tests/test_module4_generation.py` | 模块4自动化测试。 |

模块4正式调用入口：

```python
from app.generation.answer_generator import generate_answer
from app.retrieval.hybrid_retriever import retrieve

retrieval_response = retrieve(question)
result = generate_answer(question, retrieval_response)
```

旧代码仍可以直接传入证据列表：

```python
result = generate_answer(question, evidence)
```

但是旧方式无法携带模块3的澄清、降级和拒答指导，因此只用于兼容，不作为正式联调入口。

## 4. 模块3输入接口

模块3是模块4的直接上游。模块4正式接收模块3返回的完整 `RetrievalResponse`，而不是只接收一个证据数组。

输入结构示例：

```json
{
  "query": "2025年三季度商业银行资本充足率是多少？",
  "status": "answerable",
  "analysis": {
    "query_type": "table_lookup",
    "entities": {
      "metric": "资本充足率",
      "normalized_period": "2025Q3"
    }
  },
  "evidence": [],
  "diagnostics": {
    "failures": []
  },
  "module4_guidance": {
    "action": "answer",
    "may_generate_answer": true,
    "require_citations": true,
    "preserve_numeric_source_value": true
  }
}
```

### 4.1 模块3状态处理

模块4必须优先判断 `status` 和 `module4_guidance.may_generate_answer`：

| 模块3状态 | 模块4处理方式 |
|---|---|
| `answerable` | 基于证据生成答案，完成引用和字段校验。 |
| `degraded` | 可以生成答案，但必须增加检索降级风险提示。 |
| `needs_clarification` | 不生成确定性答案，返回澄清问题和可选项。 |
| `no_evidence` | 拒绝回答，不得根据常识猜测。 |

模块4不能因为某条证据向量分数较高，就绕过：

```json
{
  "may_generate_answer": false
}
```

### 4.2 证据最小字段

每条证据至少应包含：

```json
{
  "chunk_id": "doc001_clause_0001",
  "chunk_type": "clause",
  "score": 1.0,
  "text": "商业银行资本充足率不得低于8%。",
  "source": {
    "doc_id": "doc001",
    "title": "商业银行资本管理办法",
    "issuer": "国家金融监督管理总局",
    "publish_date": "2023-11-01",
    "clause_no": "第十条",
    "source_url": "",
    "local_path": "data/raw/example.docx"
  },
  "metadata": {}
}
```

表格证据还应保留：

- `sheet_name`
- `table_name`
- `cell_ref`
- `metric_name`
- `period`
- `unit`
- `value` 或 `values`
- `value_numeric`

如果 `metadata.evidence_quality.complete=false`，模块4不会补造缺失来源，而是拒答或提示证据不完整。

## 5. 模块4处理流程

模块4内部处理过程如下：

```text
接收 RetrievalResponse
   ↓
检查 status 和 may_generate_answer
   ├─ needs_clarification → 返回澄清问题
   ├─ no_evidence → 返回可信拒答
   └─ answerable/degraded → 继续处理
   ↓
标准化证据并分配 E1、E2……
   ↓
检查证据充分性和来源完整性
   ↓
生成证据约束答案
   ↓
校验数字、日期、文号、机构名、规范词和引用
   ├─ 校验通过 → 正常回答
   └─ 校验失败 → 拒绝输出未经核验的结论
   ↓
输出结构化 AnswerResult
```

### 5.1 Evidence-aware Prompt

模块4提示词的核心约束包括：

1. 只能使用给定证据回答。
2. 不得增加证据中不存在的事实或数字。
3. 每个结论必须带 `[E1]` 形式的引用。
4. 证据不足、证据冲突或问题条件不完整时不得猜测。
5. 优先输出结论，再说明依据和风险提示。

### 5.2 默认生成方式

当前模块4默认使用保守的抽取式生成器，从证据正文中组织答案，不依赖外部生成式大模型 API。

项目中的本地模型：

```text
Model/bge-small-zh-v1.5/
```

是模块2、模块3使用的 embedding 模型，负责向量检索，不是生成式大语言模型。模块4已经预留生成函数注入接口：

```python
result = generate_answer(
    question,
    retrieval_response,
    generator=my_llm_generator,
)
```

后续接入生成式模型时，无论模型返回什么内容，答案仍需经过 `verify_answer()` 校验。

### 5.3 关键字段校验

当前校验器能够检查：

- 金额和普通数值。
- 百分比和监管阈值。
- 日期和统计期间。
- 监管文件文号。
- 监管机构和金融机构名称。
- “应当、必须、不得、禁止、可以、原则上”等规范性用语。
- 答案是否包含证据引用。
- 答案是否引用了不存在的证据编号。

例如，证据写明 `8%`，如果生成器输出 `10%`，校验器会把该数字标记为证据外内容，并拒绝输出确定性结论。

### 5.4 表格比例换算

模块3保留表格源值，例如：

```text
0.15359
```

如果问题要求百分比展示，模块4可以进行确定性换算：

```text
15.359%
```

同时保留：

- 原始值 `0.15359`
- 展示值 `15.359%`
- 换算说明
- 原表单元格，例如 `D44`

这样既方便用户阅读，也能保证答案可追溯。

## 6. 模块4输出结构

模块4通过 `AnswerResult` 向模块5和模块6提供统一结果。

正常回答示例：

```json
{
  "status": "answered",
  "answer": "商业银行资本充足率为15.359%。[E1]",
  "evidence": [],
  "risk_tips": [],
  "confidence": 0.98,
  "citations": ["E1"],
  "verification": {
    "passed": true,
    "issues": [],
    "unsupported_claims": []
  },
  "question": "2025年三季度商业银行资本充足率是多少？",
  "retrieval_status": "answerable",
  "module4_guidance": {},
  "diagnostics": {}
}
```

模块4输出状态包括：

| 状态 | 含义 |
|---|---|
| `answered` | 证据充分且答案通过校验。 |
| `degraded` | 答案通过校验，但部分检索通道发生故障。 |
| `needs_clarification` | 问题缺少必要条件，需要用户补充。 |
| `no_evidence` | 知识库中没有找到可靠证据。 |
| `refused` | 证据不足、来源不完整或生成内容未通过校验。 |

所有结果均稳定包含：

- `status`
- `answer`
- `evidence`
- `risk_tips`
- `confidence`
- `citations`
- `verification`

拒答时还会提供：

- `refusal_reason`

需要澄清时还会提供：

- `clarification_question`
- `clarification_options`

## 7. 与模块5的对接

模块5是模块4的直接下游，负责后端 API、前端页面和最终演示系统。

### 7.1 调用关系

当前后端调用入口位于：

```text
app/api/main.py
```

调用链路为：

```python
from app.generation.answer_generator import generate_answer
from app.retrieval.hybrid_retriever import retrieve


def ask(question: str) -> dict:
    response = retrieve(question)
    return generate_answer(question, response)
```

因此模块5不需要重新实现答案生成、校验或拒答逻辑，只需要调用 `ask(question)`，并正确展示模块4返回的字段。

### 7.2 模块5需要展示的内容

前端建议至少展示：

1. 回答状态。
2. 最终结论。
3. 置信度。
4. 风险提示。
5. 证据编号和证据正文。
6. 文档标题、发布机构和发布日期。
7. 条款号、章节路径或表格单元格位置。
8. 原文链接或本地文件路径。
9. 拒答原因。
10. 澄清问题和可选项。

### 7.3 不同状态的前端行为

| 状态 | 前端建议行为 |
|---|---|
| `answered` | 展示答案、证据、引用、置信度和校验通过状态。 |
| `degraded` | 正常展示答案，同时突出显示检索降级风险。 |
| `needs_clarification` | 不展示确定性答案，展示澄清问题和选项按钮。 |
| `no_evidence` | 展示可信拒答，不展示伪造引用。 |
| `refused` | 展示拒答原因和校验失败详情。 |

模块5不能把所有状态都压缩成“成功/失败”两种结果，否则会丢失模块4的可信控制信息。

### 7.4 当前前端联调状态

Streamlit 原生问答调试模式已经直接调用 `app.api.main.ask()`，可用于验证真实模型、知识库和模块4输出。

现代三栏 HTML 前端的 `APIService.baseUrl` 当前为空，因此默认走 Mock 数据。模块5后续需要：

1. 提供正式 HTTP `/api/v1/ask` 接口。
2. 配置前端 `baseUrl`。
3. 映射 `needs_clarification`、`no_evidence` 和 `degraded` 状态。
4. 使用模块4实际返回的 `verification`，不能在前端固定写“已核验”或固定置信度。

## 8. 与模块6的对接

模块6负责评测、实验、报告和答辩材料。模块4需要向模块6提供可批量统计的结构化结果。

### 8.1 可直接评测的字段

| 模块4字段 | 可计算指标 |
|---|---|
| `status` | 回答率、拒答率、澄清率、检索降级率。 |
| `answer` | 答案正确率和关键事实准确率。 |
| `citations` | 引用覆盖率和引用编号正确率。 |
| `evidence` | 证据命中率、来源完整率和证据可追溯率。 |
| `confidence` | 置信度分布和校准误差。 |
| `verification.passed` | 校验通过率。 |
| `verification.unsupported_claims` | 未支持声明数量和关键字段错误率。 |
| `refusal_reason` | 拒答原因分布和拒答准确率。 |
| `retrieval_status` | 模块3状态与模块4输出状态的一致性。 |

### 8.2 建议评测指标

模块6建议至少统计：

1. 答案准确率。
2. 证据命中率。
3. 引用正确率。
4. 关键数字正确率。
5. 规范性表达一致率。
6. 拒答准确率。
7. 澄清触发准确率。
8. 无证据问题的安全拦截率。
9. 平均生成与校验耗时。

### 8.3 建议评测样例

评测集需要同时包含：

- 可以正常回答的制度事实题。
- 条款阈值题。
- 明确期间的表格取数题。
- 缺少季度、银行档次或统计口径的问题。
- 知识库范围外的问题。
- 故意提供错误数字的生成结果。
- 多文档或证据冲突问题。

模块6不能只判断 `status=answered`，还必须检查答案中的指标名称、数字、时间、适用对象和引用证据是否一致。

- 引用存在性校验。
- 来源完整性检查。
- 拒答和澄清机制。
- 表格比例换算与源值保留。

## 10. 当前边界与后续工作

按照六人分工文档中“稳定输出结论、依据、证据来源、风险提示和拒答结果”的基础标准，模块4核心交付已经完成。

但最终比赛系统仍需要继续完成：

1. 根据团队选型接入具体生成式大模型或云端 API。
2. 为生成模型调用增加超时、重试和耗时统计。
3. 使用正式评测集校准置信度和证据充分性阈值。
4. 增强相近指标的精确语义校验，例如区分“资本充足率”和“核心一级资本充足率”。
5. 增强复杂跨文档推理和证据冲突检测。
6. 完成现代三栏前端与真实后端 API 的联调。
7. 与模块6确定答案准确率、拒答准确率和关键字段错误率的统一评分规则。

模块4只能保证答案不超出输入证据，但最终答案是否正确仍依赖模块3提供的证据是否精确。例如，用户询问“资本充足率”时，上游不能只返回“核心一级资本充足率”的条款。模块3需要做好指标精确匹配，模块4也需要继续增强问题指标和证据指标的一致性检查。

## 12. 总结

模块4已经完成从“检索证据”到“可信结构化回答”的基本闭环：

```text
模块3证据输入
   ↓
证据标准化与引用编号
   ↓
证据约束答案生成
   ↓
数字和关键字段校验
   ↓
正常回答 / 降级提示 / 请求澄清 / 可信拒答
   ↓
模块5展示与模块6评测
```

模块4最关键的价值不是让系统“每个问题都回答”，而是让系统做到：

> 有可靠证据时给出可追溯答案，没有可靠证据时明确拒答或请求用户补充条件。
