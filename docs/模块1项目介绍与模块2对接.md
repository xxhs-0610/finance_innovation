# 模块1项目介绍与模块2对接

## 1. 文档目的

本文说明“文档解析模块（模块1）”当前的完成情况、项目结构、运行方式、数据库和 JSONL 产物，并明确“知识库构建与索引模块（模块2）”应使用哪些数据。

结论：模块1已经完成当前赛题数据集的全量解析和落库，并已通过一次真实全量的模块1到模块2构建验证。模块2可以直接使用模块1导出的 `parsed_docs.jsonl` 和 `table_evidence.jsonl`，不应默认读取体积较大的完整单元格归档 `parsed_tables.jsonl`。

## 2. 完成情况评估

### 2.1 已完成能力

- 支持 `.doc`、`.docx`、`.pdf`、`.xls`、`.xlsx` 五类附件。
- 对源文件生成稳定 `doc_id`、SHA-256、文件类型、文件大小和本地 manifest。
- Word 解析保留标题、段落、章节、条款和表格的原始顺序。
- 旧版 DOC 优先使用 LibreOffice 转换，Windows 下可使用 Word COM 后备。
- PDF 保留页码、文本位置和表格；低文本页可调用 RapidOCR。
- Excel 保留 sheet、多级表头、合并单元格、期间、单位、指标、公式、原始值、显示值和规范化值。
- 超大工作簿使用单元格迭代器和分批数据库写入，避免一次性加载百万单元格。
- 支持增量解析、指定格式或文档解析、强制重建、失败重试和幂等写入。
- 每个文档独立事务写入，单个文档失败不会影响其他文档。
- MySQL 保存规范化全量数据，JSONL 作为模块间交付和离线复现接口。
- 可生成解析质量报告，并能从正文或表格证据回溯原文件、页码或单元格。

#### 为什么附件编号到了 507，但报告只有 500 个文件

`nfra_page_attachments_500/` 中的附件文件名编号范围是 `1–507`，但编号并不连续。原始数据中没有以下 7 个编号：

```text
436、437、438、439、440、442、450
```

因此实际有效附件数量为 `507 - 7 = 500`。盘点结果还确认这 500 个文件的编号均唯一，没有因为重号造成少计。模块1报告中的“500”是对目录中实际存在文件的计数，不是根据最大编号推算的数量。

赛题目录还单独包含一个 `QA数据.xlsx`，其中有 300 道问答样本。它属于评测数据，应放入 `data/raw/qa/`，不属于 `data/raw/nfra_page_attachments_500/` 的监管知识附件，也不进入模块1的附件解析统计。因此：

- 监管知识附件：500 个，模块1已全部盘点和解析。
- QA 数据文件：1 个，由后续评测数据处理流程使用。
- 若同时统计这两类有效赛题数据文件，则是 501 个，而不是 507 个。

原压缩包中的 `__MACOSX/._*` 文件是 macOS 生成的资源分叉元数据，不是有效 Word、PDF 或 Excel 数据，也不会进入解析。

两个部分成功文件为 `nfra_att_373` 和 `nfra_att_374`。它们是保险市场年报 PDF，少数封面或图片页没有可识别文本，但其余可解析页面已经正常入库。因此这不是全文件失败，也不阻断模块2构建。

## 4. 数据存储设计：MySQL 与 JSONL 是否都保留

建议保留两种存储形式，不删除其中任何一种，但必须明确职责，避免重复使用和职责混淆。

```text
原始 Word / PDF / Excel
          │
          ▼
模块1解析与规范化
          │
          ▼
MySQL：finance_innovation_rag（唯一规范事实源）
          │
          ├──────────────► 质量核验、增量更新、问题追踪、精确回查
          │
          ▼
流式导出 JSONL（稳定交付快照）
          │
          ├─ parsed_docs.jsonl ───────┐
          └─ table_evidence.jsonl ────┼─► 模块2构建 chunk、元数据仓库和检索索引
                                      │
parsed_tables.jsonl ─► 审计/复核/再生成证据，不进入默认建库链路
doc_meta.jsonl ──────► 元数据快照和审计，当前模块2无需单独读取
```

### 4.1 MySQL 的职责

MySQL 数据库 `finance_innovation_rag` 是模块1的唯一规范事实源，适合：

- 保存文档、正文块、表格和百万级单元格之间的规范化关系。
- 记录解析批次、活动版本、失败问题和重试状态。
- 支持增量更新、幂等写入、质量查询和精确溯源。
- 在证据组织策略变化时重新导出 JSONL，而不必重跑全部原文件解析。

模块1不会读取或修改 `finance_risk` 和 `finance_risk_data`。

### 4.2 JSONL 的职责

JSONL 是模块间的数据契约和可移植快照，适合：

- 让模块2不依赖模块1数据库账号、表结构和在线连接。
- 流式读取，降低大数据集的内存占用。
- 固化某次实验的数据版本，便于复现和团队协作。
- 在不同机器上转移模块1交付物。

因此不建议让模块2直接查询模块1的 MySQL。模块边界使用 JSONL 更稳定，也避免数据库结构变化影响检索建库代码。

## 5. MySQL 数据库说明

数据库名称默认为 `finance_innovation_rag`，字符集为 `utf8mb4`。密码仅通过环境变量 `RAG_DB_PASSWORD` 传入。

| 表名 | 主要内容 |
|---|---|
| `rag_schema_migrations` | 数据库结构版本和迁移记录。 |
| `rag_parse_runs` | 解析批次、模式、配置、时间及成功/部分成功/失败统计。 |
| `rag_documents` | 文件元数据、标题、机关、文号、日期、哈希、路径、状态和重复文件关系。 |
| `rag_document_blocks` | 标题、章节、条款、段落、页码、层级路径、正文和原文定位。 |
| `rag_tables` | sheet、页码、表名、范围、单位、期间、表头、规模和合并区域。 |
| `rag_table_cells` | 单元格坐标、行列表头、指标、期间、单位、公式、原始值、显示值和规范化值。 |
| `rag_parse_issues` | 解析阶段、错误码、严重程度、上下文和是否可重试。 |

数据库中的正文块、表格和单元格均带稳定 ID 和 `is_active` 状态。重新解析时旧记录被标记为非活动，当前记录通过 upsert 写入，不采用删除整个数据库后重建的方式。

## 6. 模块1使用说明

所有命令应在 `finance_innovation/` 项目根目录执行。

### 6.1 安装依赖

```powershell
pip install -r requirements.txt
```

旧 DOC 建议安装 LibreOffice。PDF 图片页 OCR 需要 `rapidocr_onnxruntime` 和 `PyMuPDF`；Windows 使用 Word COM 后备时需要安装 Microsoft Word 和 `pywin32`。

### 6.2 配置本地 MySQL

非敏感默认配置位于 `configs/parsing.json`。设置环境变量：

```powershell
$env:RAG_DB_HOST="127.0.0.1"
$env:RAG_DB_PORT="3306"
$env:RAG_DB_USER="root"
$env:RAG_DB_PASSWORD="你的本地MySQL密码"
$env:RAG_DB_NAME="finance_innovation_rag"
```

真实密码不得写入源码、JSON 配置、README 或 `.env.example`。

### 6.3 标准运行流程

```powershell
# 1. 检查路径、依赖和数据库连接
python scripts/parse_documents.py check

# 2. 如数据仍在项目外，复制到既定 raw 目录
python scripts/parse_documents.py sync-raw

# 3. 创建数据库和表
python scripts/parse_documents.py init-db

# 4. 盘点文件并生成 manifest
python scripts/parse_documents.py inventory

# 5. 增量解析全部待处理或发生变化的文件
python scripts/parse_documents.py parse --all

# 6. 导出模块2正式输入和元数据
python scripts/parse_documents.py export-jsonl

# 7. 生成质量报告
python scripts/parse_documents.py report
```

### 6.4 常用增量和故障处理命令

```powershell
# 只重试 failed 或 partial 文件
python scripts/parse_documents.py parse --retry-failed

# 强制重新解析全部文件
python scripts/parse_documents.py parse --force

# 只解析 PDF
python scripts/parse_documents.py parse --file-type pdf

# 只解析指定稳定 doc_id
python scripts/parse_documents.py parse --doc-id nfra_att_373

# 解析后立即导出默认 JSONL
python scripts/parse_documents.py parse --all --export-jsonl

# 额外重新生成完整单元格审计归档
python scripts/parse_documents.py export-jsonl --include-cell-archive
```

`export-jsonl` 默认不重复生成约 1 GB 的 `parsed_tables.jsonl`，因为模块2不需要逐单元格建索引。仅在审计、抽样核验或需要重新组织表格证据时使用 `--include-cell-archive`。

## 7. 模块1生成数据说明

### 7.1 `data/parsed/docs/parsed_docs.jsonl`

作用：模块2的制度正文正式输入。每行是一条可检索正文证据，主要字段包括：

- `block_id`：稳定正文块 ID，模块2将其作为 chunk ID。
- `doc_id`、`title`、`issuer`、`document_no`、`publish_date`：文档身份和监管元数据。
- `block_type`、`section_path`、`clause_no`、`text`：正文类型、章节层级、条款号和内容。
- `page_no`、`bbox`、`source_locator`：页码、坐标或原始顺序等定位信息。
- `source_url`、`local_path`：来源链接和本地原文件路径；无真实来源链接时 `source_url` 为 `null`，不伪造。

当前文件约 18.4 MB，共 22,880 条导出正文记录。数据库活动正文块数量更高，是因为表格占位等非正文检索块不会全部进入模块2正文输入。

### 7.2 `data/parsed/tables/table_evidence.jsonl`

作用：模块2的表格正式输入。当前约 262 MB，共 102,286 条记录，其中：

- `table_summary`：1,110 条，描述表名、sheet、期间、单位、范围和行列规模。
- `table_row`：101,176 条，将同一表格行拆成最多 20 个单元格的证据分段。

主要字段包括：

- `evidence_id`、`record_type`、`doc_id`、`table_id`。
- `title`、`sheet_name`、`table_name`。
- `row_index`、`cell_range`、`metric_name`、`period`、`unit`。
- `values`：该证据包含的值、表头和原始 `cell_ref`。
- `retrieval_text`：已经组织好的检索文本。
- `source_url`、`local_path`：来源定位。

该文件把 1,157,751 条完整单元格归档压缩组织为 102,286 条检索证据，既保留单元格坐标，又避免超大工作簿产生百万个低语义密度 chunk。

### 7.3 `data/parsed/tables/parsed_tables.jsonl`

作用：可选的完整单元格审计归档，不是模块2默认输入。

每行对应一个活动单元格，保留 `sheet_name`、`table_name`、`cell_ref`、行列表头、指标、期间、单位、公式、原始值、显示值和规范化数值。当前约 1.07 GB，共 1,157,751 行。

该文件适用于：

- 抽样对照原始 Excel 单元格。
- 不连接 MySQL 时进行离线审计。
- 研究新的表格证据组织策略。

MySQL 才是完整数据的规范事实源；该文件可以随时从 MySQL 重新导出，因此不应作为数据库的替代品，也不应直接用于默认知识库构建。

### 7.4 `data/parsed/meta/doc_meta.jsonl`

作用：500 个源文件的元数据和解析状态快照。主要包含 `doc_id`、文件名、格式、大小、SHA-256、标题、机关、文号、日期、路径、解析器、状态和重复文件关系。

当前模块2从正文和表格证据中直接获取建库所需元数据，因此无需单独读取该文件。它主要用于盘点、审计、状态检查和后续数据治理。

### 7.5 `data/parsed/meta/generated_manifest.jsonl`

作用：原始文件盘点清单，记录稳定 ID、文件路径、哈希和基础文件信息。它用于确认 500 个文件是否全部被发现，以及识别重复或发生变化的文件，不进入模块2知识库。

### 7.6 `reports/module1_parsing_report.md`

作用：汇总文件格式、解析状态、正文块、表格、单元格、警告和部分成功/失败文件，用于交付验收和问题追踪。

## 8. 模块2应使用哪些数据

模块2只需要以下两个正式输入：

| 模块1产物 | 模块2用途 | 是否必需 |
|---|---|---|
| `data/parsed/docs/parsed_docs.jsonl` | 生成法规/制度正文 clause chunk | 是 |
| `data/parsed/tables/table_evidence.jsonl` | 生成表摘要和行级 table chunk | 是 |
| `data/parsed/meta/doc_meta.jsonl` | 全量文件盘点和审计；当前建库信息已嵌入前两个文件 | 否 |
| `data/parsed/tables/parsed_tables.jsonl` | 完整单元格核验和证据重组 | 否，禁止作为默认输入 |
| MySQL `finance_innovation_rag` | 模块1事实源和精确回查 | 否，模块2不直接依赖 |

模块2全量运行路径配置在 `configs/default.json`：

```json
{
  "paths": {
    "parsed_docs": "data/parsed/docs/parsed_docs.jsonl",
    "parsed_tables": "data/parsed/tables/table_evidence.jsonl"
  }
}
```

这里保留了配置键名 `parsed_tables` 以兼容已有模块2代码，但它的实际文件已经切换为检索级 `table_evidence.jsonl`。

项目只使用这一套正式路径，不设置第二套样例配置或交付目录。Git 是否跟踪文件只影响文件如何传到成员电脑，不改变程序读取路径。

其中模块2只需要第一个文件。文件放好后不需要修改 `configs/default.json`、源码或命令参数。这样所有成员始终使用同一个仓库、同一套配置和同一套目录契约。

## 9. 模块2构建方式与输出

确认 Git 中的 `parsed_docs.jsonl` 已存在，并把大文件 `table_evidence.jsonl` 放入标准目录后执行：

```powershell
python scripts/build_kb.py
```

模块2会流式读取两个 JSONL，避免把全量记录一次性载入内存，并生成：

```text
data/processed/
├─ clause_chunks.jsonl   # 正文 chunk
├─ table_chunks.jsonl    # 表格 chunk
└─ metadata.db           # chunk 元数据 SQLite 数据库

indexes/
└─ bm25_corpus.jsonl     # 关键词检索语料
```

处理映射如下：

```text
parsed_docs.jsonl
    └─ app/indexing/chunk_clauses.py
          └─ clause_chunks.jsonl

table_evidence.jsonl
    └─ app/indexing/chunk_tables.py
          └─ table_chunks.jsonl

全部 chunk
    ├─ metadata.db
    └─ bm25_corpus.jsonl
```

表格证据中的稳定 `evidence_id` 会作为模块2的 `chunk_id`。模块2同时保留 `record_type`、`table_id`、`row_index`、`cell_range` 和 `values`，后续模块可以返回单元格级可信引用。

## 11. 当前限制与后续建议

- `nfra_att_373`、`nfra_att_374` 的少数图片页无法识别文字，当前标记为 `partial`。若这些页面包含关键内容，可增加更强 OCR 或人工补录；其余页面已可用于模块2。

- 当前表格证据采用“表摘要 + 行级最多 20 个单元格”的通用策略。模块2可以依据真实 QA 的取数模式继续优化列组合、跨行表头和宽表召回，但不需要修改模块1的规范化数据库。
- 大型 JSONL 和索引产物不提交 Git。取得大文件后必须放回本文约定的固定目录，不新增个人路径或第二套配置，并记录解析批次和文件哈希。

## 12. 最终判断

模块1已经完成当前阶段要求，并能够直接向模块2交付数据。保留 MySQL 与 JSONL 是合理设计，不需要删除任一形式：MySQL 负责完整、规范化、可增量的数据管理，JSONL 负责稳定、解耦、可流式读取的模块间交付。

模块2正式且唯一需要关注的模块1建库输入是：

1. `data/parsed/docs/parsed_docs.jsonl`
2. `data/parsed/tables/table_evidence.jsonl`

`parsed_tables.jsonl` 仅作为完整单元格审计归档，`doc_meta.jsonl` 仅作为文件元数据快照；二者都不应加入模块2默认建库流程。

所有成员统一运行 `python scripts/build_kb.py`，统一读取 `configs/default.json`，不使用 `--sample` 或其他交付配置。
