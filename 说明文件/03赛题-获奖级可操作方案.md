# 03赛题获奖级可操作方案

## 1. 方案定位

### 1.1 赛题名称
面向银行业监管制度与统计报表的可信 RAG 问答

### 1.2 我们的目标
围绕赛题要求，做出一个不是“能答几个问题”的通用问答 Demo，而是一个面向银行监管知识检索场景、可追溯、可核验、可拒答、可复现的垂域可信 RAG 系统。

### 1.3 获奖级方案的判断标准
这道题要想做得像获奖作品，核心不是模型堆料，而是做到下面五点同时成立：

1. 题目要求完整闭环：文档解析、知识库、检索、生成、证据引用、评测报告、复现实验脚本都齐。
2. 监管场景贴合：能处理制度条款、金额阈值、期限、适用对象、禁止性规定、统计表格取数、跨文件判断。
3. 可信能力突出：有证据链、有拒答机制、有版本控制、有数字校验，不靠“大模型感觉对”。
4. 工程落地清晰：系统架构明确、接口清晰、可运行、可扩展到 200+ 文件。
5. 答辩叙事强：能讲清楚“为什么这样设计”“为什么比普通 RAG 更适合银行监管场景”。

一句话概括本方案：

**做一个“监管条款 + 统计表格”双知识底座、混合检索、证据约束生成、结果核验与拒答联动的可信 RAG 系统。**

## 2. 题目拆解

### 2.1 赛题明确要求

根据题面，系统必须解决两大任务：

1. 监管文档解析与索引。
2. 可溯源问答生成。

### 2.2 题目重点考察能力

题面明确提到了六个重点：

1. 金融监管知识理解
2. 复杂表格解析
3. 跨文件检索
4. 多跳推理
5. 答案可验证性
6. 幻觉抑制能力

### 2.3 量化指标

建议目标至少按题面指标上浮半档来设计：

| 指标 | 赛题底线 | 我们的目标 |
|---|---:|---:|
| 制度事实类准确率 | >= 85% | >= 90% |
| 表格取数类准确率 | >= 80% | >= 86% |
| 证据引用命中率 | >= 90% | >= 95% |
| 关键数字/日期/机构/文号错误率 | <= 5% | <= 2% |
| 库外或依据不足问题拒答/澄清率 | >= 80% | >= 90% |

### 2.4 数据条件

题面给出的数据基础其实很适合做出完整闭环：

1. 100 个 Word/PDF/附件混合监管文件
2. 100 个 Excel 统计附件
3. 20 份重点监管文件目录
4. 42 条种子问答样本
5. manifest 元信息，包括 URL、本地路径、SHA-256、标题、doc_id 等

这意味着你们的方案必须充分利用 `manifest`，把“溯源”和“版本管理”做成显式能力，而不是只把文档塞进向量库。

## 3. 获奖方案总路线

### 3.1 总体思路

系统采用六层架构：

1. 文档接入层
2. 结构化解析层
3. 双知识库构建层
4. 混合检索与证据编排层
5. 受约束生成与结果核验层
6. 评测与演示层

### 3.2 核心差异化亮点

普通 RAG 往往是“切块 + 向量检索 + 大模型生成”。这题要获奖，必须显著高于普通 RAG。建议把亮点集中在下面五个点：

1. **条款级与表格级双通道知识建库**
   不把 Excel 当普通文本处理，而是单独做表格结构知识表示。

2. **面向监管问答的混合检索**
   把 BM25、向量检索、元数据过滤、条款编号检索、表格结构检索联合起来。

3. **证据优先生成**
   先找最小充分证据，再受约束生成答案，不允许无依据自由发挥。

4. **数字与规范表达校验**
   对金额、比例、日期、文号、机构名、规范强度词做二次校验。

5. **拒答与澄清机制**
   对库外问题、证据不足问题、版本冲突问题主动拒答或要求澄清。

### 3.3 最终产品形态

最终展示不建议只做一个聊天框，而要做成“三件套”：

1. 一个问答前端 Demo
2. 一个可复现的离线评测与报告系统
3. 一个可解释的证据追溯页面

这样答辩时既能演示“能答”，又能演示“为什么可信”。

## 4. 系统架构设计

### 4.1 整体链路

```text
官方文档/表格
  -> 文档解析
  -> 结构化切分
  -> 条款库/表格库/元数据库
  -> 意图识别
  -> 混合检索
  -> 证据重排
  -> 受约束生成
  -> 数字与证据校验
  -> 输出答案/证据/置信度/拒答原因
```

### 4.2 文档解析层

这一层是成败关键。建议单独做成可复用模块。

#### A. Word/PDF 制度文件解析

抽取以下对象：

1. 文件级信息：`doc_id`、标题、发文机关、发布日期、来源 URL、文件类型、版本标识
2. 结构级信息：篇、章、节、条、款、项
3. 语义级信息：定义条款、适用范围、禁止性规定、金额阈值、期限要求、流程要求

#### B. Excel 统计附件解析

不要只转成纯文本，必须保留表结构：

1. 表名
2. 页签名
3. 表头多级层次
4. 行列索引
5. 指标名称
6. 单位
7. 期间维度
8. 单元格值
9. 口径备注

建议形成“表格单元证据对象”，最小粒度至少到单元格或单元格组。

### 4.3 双知识库设计

建议拆成三库，不要只做一个向量库：

1. **条款库**
   面向制度原文，最小粒度到条款或段落。

2. **表格库**
   面向 Excel 统计附件，最小粒度到表、行、列、单元格组。

3. **元数据库**
   存放 `doc_id`、标题、发布日期、发文机关、主题、业务条线、版本状态、来源 URL、SHA-256。

这样做的价值是：

1. 支持按文号、文件名、时间、主题过滤
2. 支持新旧版本识别
3. 支持表格与正文联动检索
4. 支持答辩时解释“为什么这个答案可信”

### 4.4 问题分类器

在进入检索前先做问题分类，按题面建议的五类问题建立路由：

1. 制度事实题
2. 条款/阈值题
3. 业务流程题
4. 统计表格取数题
5. 跨文件场景判断题

分类器作用：

1. 决定走条款检索还是表格检索为主
2. 决定是否需要多跳推理
3. 决定最终答案模板
4. 决定评测口径

## 5. 关键技术方案

### 5.1 文档切分策略

不要统一固定长度切块，建议采用“结构优先切分”：

1. 制度正文按章节和条款编号切分
2. 附件表格按表头和逻辑区域切分
3. 对条款定义、阈值、期限类句子再做细粒度标签化

推荐保留的字段：

1. `chunk_id`
2. `doc_id`
3. `section_path`
4. `clause_no`
5. `table_name`
6. `sheet_name`
7. `metric_name`
8. `period`
9. `unit`
10. `publish_date`
11. `effective_scope`

### 5.2 混合检索策略

建议采用四阶段检索：

#### 阶段一：查询理解

识别：

1. 问题类型
2. 业务主题
3. 关键词
4. 条款编号
5. 指标名称
6. 时间维度
7. 是否涉及比较、判断、计算

#### 阶段二：召回

联合使用：

1. BM25 关键词召回
2. 向量语义召回
3. 元数据过滤召回
4. 表格结构召回

#### 阶段三：重排

用 reranker 按“问题-证据匹配度”重排，优先保留：

1. 最新有效文件
2. 条款编号完全匹配的证据
3. 指标名和期间匹配的表格证据
4. 同时包含定义和限制条件的最小充分证据

#### 阶段四：证据包构造

每次生成前只提供有限、精选、带来源标识的证据，不给模型一堆冗余上下文。

### 5.3 生成策略

生成必须采用“证据约束模板”，答案结构建议统一为：

1. 直接答案
2. 依据说明
3. 证据出处
4. 风险提示
5. 置信度

示例输出结构：

```json
{
  "answer": "...",
  "evidence": [
    {
      "doc_id": "...",
      "source_title": "...",
      "location": "第X条/SheetY/单元格区域",
      "quote": "..."
    }
  ],
  "reasoning_type": "single-hop | multi-hop | table-lookup | compliance-judgement",
  "risk_note": "...",
  "confidence": 0.91
}
```

### 5.4 幻觉抑制与可信机制

这一部分是答辩重点，建议作为核心创新来讲。

#### 机制一：证据不足拒答

满足任一条件则拒答：

1. 检索分数低于阈值
2. 证据冲突无法判定
3. 找不到明确条款或表格依据
4. 问题超出知识库范围

#### 机制二：关键字段校验

对以下字段做抽取后校验：

1. 金额
2. 比例
3. 日期
4. 期限
5. 机构名称
6. 文号
7. “应当/不得/可以/原则上”等规范强度词

#### 机制三：版本优先级控制

当同名文件出现多个版本时，优先最新有效版本，并显式提示：

1. 当前采用的版本
2. 是否存在历史版本
3. 是否可能影响结论

#### 机制四：场景判断分两步

对“合规判断类”问题，不直接一步生成。

流程改为：

1. 先抽取规则条件
2. 再比对业务事实
3. 最后输出判断与依据

这样可以显著降低“看似合理但没证据”的错误。

### 5.5 跨文件多跳推理

这是最容易拉开差距的部分。建议显式设计成两段式：

1. 从制度文件中找到指标定义、适用口径、取值规则
2. 去统计表中按口径和期间取数
3. 回到生成层输出“定义 + 数据 + 解释”

答辩时可以用一个典型例子展示：

“某监管指标在什么口径下定义？2024 年某季度该指标取值是多少？如果变化明显，原因是什么？”

如果你们能现场走通这一条链路，会很像高质量作品。

## 6. 评测体系设计

### 6.1 评测集构造

在题面 42 条种子问答基础上，扩充到 150-250 条内部评测集，覆盖五类问题。

建议比例：

1. 制度事实题：25%
2. 条款/阈值题：25%
3. 流程题：15%
4. 表格取数题：20%
5. 跨文件场景判断题：15%

### 6.2 评测维度

每条样本至少评五项：

1. 答案正确性
2. 证据命中情况
3. 最小充分证据率
4. 关键字段错误情况
5. 是否应拒答且是否正确拒答

### 6.3 核心评测指标

建议形成以下指标面板：

1. Top-1 证据命中率
2. Top-3 证据覆盖率
3. Answer Exact Match 或规则匹配准确率
4. 数字字段准确率
5. 规范用语准确率
6. 拒答准确率
7. 平均响应时延

### 6.4 对比实验

获奖作品通常会有清楚的 ablation。建议至少做四组：

1. 仅 BM25
2. 仅向量检索
3. BM25 + 向量 + 元数据过滤
4. 完整方案：混合检索 + 重排 + 证据约束生成 + 校验拒答

这样能很清楚证明你们不是“换个模型碰运气”，而是系统设计真的有效。

## 9. 推荐技术栈

默认按“实现快、工程稳、比赛好交付”原则，建议优先 Python。

### 9.1 后端

1. Python
2. FastAPI
3. SQLite 或 PostgreSQL

### 9.2 检索

1. BM25：Elasticsearch / OpenSearch / Whoosh
2. 向量库：FAISS / Milvus
3. rerank：bge-reranker 或同类中文 reranker

### 9.3 解析

1. PDF：pdfplumber / pymupdf
2. Word：python-docx
3. Excel：openpyxl / pandas

### 9.4 大模型

策略建议：

1. 检索和重排优先用轻量稳定模型
2. 生成层可接通用中文大模型
3. 不把“换更大模型”作为主要卖点

比赛里更有说服力的是“可信机制”和“场景适配”，不是单纯参数量。

## 10. 答辩时要重点讲的创新点

建议答辩统一围绕一句主线：

**我们不是在做通用 RAG，而是在做银行监管场景下可核验、可追责、可拒答的可信问答系统。**

重点讲四个创新：

1. **双知识底座**
   条款知识和表格知识分治建模。

2. **混合检索**
   关键词、语义、元数据、结构化表格联合召回。

3. **证据约束生成**
   答案必须绑定证据，不允许脱离依据自由发挥。

4. **结果校验与拒答**
   对数字和规范性表达做校验，对不确定问题拒答。

如果时间允许，再补一个“跨文件多跳推理”的案例，会很加分。

## 12. 风险点与规避策略

### 风险一：Excel 解析做得太浅

后果：
表格题准确率上不去。

规避：
把表头层级、单位、期间、指标名作为一等公民建模。

### 风险二：只做向量检索

后果：
条款编号、文号、金额阈值类问题容易翻车。

规避：
必须上混合检索和元数据过滤。

### 风险三：生成好看但证据不稳

后果：
答辩时经不起追问。

规避：
把证据链展示和关键字段校验做成强约束。

### 风险四：没有拒答机制

后果：
库外问题和证据不足问题会产生高风险幻觉。

规避：
把拒答率作为显式指标纳入评测。

### 风险五：没有对比实验

后果：
技术方案显得像拼装，而不是研究结果。

规避：
至少做 3-4 组消融对比。

## 13. 建议的演示脚本

演示时不要随机问，建议准备 5 个固定场景：

1. 制度定义题
   展示条款级证据返回。

2. 阈值题
   展示金额、比例、期限等精确抽取。

3. 流程题
   展示流程条款和适用范围识别。

4. 表格取数题
   展示 Excel 结构检索和单元格证据。

5. 跨文件场景判断题
   展示制度口径 + 统计取数 + 结论说明。

每个演示页面都要显示：

1. 最终答案
2. 证据来源
3. 定位位置
4. 是否经过校验
5. 置信度或拒答原因

RegTrust-RAG: 面向银行监管制度与统计报表的双知识底座可信问答系统

## 15. 结论

这道 03 题的优势在于：

1. 业务价值明确
2. 技术路径清晰
3. 数据形态丰富但边界清楚
4. 很适合做出完整工程闭环
5. 很容易通过“可信、可追溯、可拒答、可复现”建立差异化

因此，最优策略不是盲目追求最强模型，而是：

**围绕监管场景做结构化解析、混合检索、证据约束生成和可信校验，把系统做完整，把评测做扎实，把答辩故事讲硬。**

这条路线最像获奖作品，也最容易真正落地。
