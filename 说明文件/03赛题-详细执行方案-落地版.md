# 03赛题详细执行方案（落地版）

这版不是讲思路，而是讲怎么开工、谁做什么、用什么技术、最后怎么拼成一个完整作品。

## 1. 最终要做成什么

最终交付不是单个模型，也不是单个脚本，而是一套完整作品，包含 6 个部分：

1. 一个可运行的监管问答系统前端
2. 一个后端问答服务 API
3. 一套离线知识库构建与更新流水线
4. 一套评测脚本与评测报告
5. 一套可复现部署环境
6. 一份能答辩的技术文档和 PPT

最后合并出来的成品可以理解为：

```text
RegTrust-RAG
  = 文档解析流水线
  + 条款/表格双知识库
  + 混合检索问答服务
  + 证据追溯与拒答机制
  + 前端演示系统
  + 离线评测与报告
```

## 2. 我们做的系统边界

这题不要做成“大而全智能体平台”，要做成一个边界清楚、可演示、可评测、可信的垂域 RAG 系统。

系统只做这五类问题：

1. 制度事实题
2. 条款/阈值题
3. 业务流程题
4. 表格取数题
5. 跨文件场景判断题

系统不做：

1. 开放域聊天
2. 联网搜索
3. 真正业务系统写回
4. 复杂 Agent 自主操作

这样能保证作品聚焦，且容易把指标做上去。

## 3. 技术总架构

建议直接按下面这套架构做，不要来回改方向。

### 3.1 系统结构

```text
原始文件
  -> 解析层
  -> 结构化中间层
  -> 知识库构建层
  -> 检索服务层
  -> 生成与校验层
  -> 前端展示层
  -> 评测层
```

### 3.2 六个核心模块

1. 文档解析模块
2. 结构化知识构建模块
3. 混合检索模块
4. 生成与可信校验模块
5. 前端展示模块
6. 评测与报告模块

## 4. 明确技术选型

下面这套是“实现快、稳定、答辩也说得过去”的组合。

### 4.1 后端与服务

1. `Python 3.11`
2. `FastAPI`
3. `Uvicorn`
4. `Pydantic`

原因：

1. 开发快
2. 适合比赛
3. API 文档自动生成
4. 后面接前端和评测都方便

### 4.2 文档解析

1. Word：`python-docx`
2. PDF：`PyMuPDF` 或 `pdfplumber`
3. Excel：`openpyxl` + `pandas`
4. OCR 兜底：如无扫描件可先不做，若有扫描件再补 `PaddleOCR`

结论：
第一版优先保证规则解析和结构提取，不要一开始就陷进 OCR。

### 4.3 检索与索引

1. 关键词检索：`BM25`，可用 `rank-bm25` 或 `Elasticsearch`
2. 向量检索：`FAISS`
3. 嵌入模型：中文通用 embedding 模型
4. 重排模型：`bge-reranker` 类 rerank 模型

建议：

1. 如果时间紧，用 `FAISS + rank-bm25`
2. 如果要更强工程展示，再上 `Elasticsearch`

比赛优先方案：

1. 离线构建：`FAISS + BM25`
2. 在线服务：本地加载索引

### 4.4 数据存储

1. 元数据表：`SQLite`
2. 结构化中间文件：`JSONL`
3. 检索索引：`FAISS index`
4. 原始文件清单：`manifest.csv/jsonl`

理由：

1. 足够支撑 200 份文件
2. 易复现
3. 不依赖复杂部署

### 4.5 前端

推荐两种方案，二选一：

1. 快速版：`Streamlit`
2. 展示版：`React + Ant Design`

建议：

如果你们核心是比赛效果和时间效率，先上 `Streamlit`。  
如果队里有前端同学且时间够，再做 `React`。

### 4.6 大模型调用

建议模型职责拆开：

1. 问题分类：小模型或规则
2. 生成回答：主生成模型
3. 不要让模型承担检索逻辑

关键原则：

1. 检索靠工程
2. 生成靠模型
3. 可信靠校验

## 5. 模块拆解到“具体做什么”

## 5.1 模块 A：文档解析模块

### 目标

把 Word/PDF/Excel 原始文件解析成统一结构。

### 输入

1. 原始文件目录
2. manifest 文件

### 输出

1. `parsed_docs.jsonl`
2. `parsed_tables.jsonl`
3. `doc_meta.db`

### 要做的事

1. 读取 manifest
2. 识别文件类型
3. 提取标题、文号、发文机关、发布日期、来源 URL
4. 对 Word/PDF 提取章节、条款、段落编号
5. 对 Excel 提取 sheet、表头、行列、单元格值、单位、时间维度
6. 统一生成 `doc_id`

### 技术要求

1. 保留条款编号
2. 保留表头层级
3. 保留时间维度
4. 保留原文件定位信息

### 完成标准

1. 200 份文件都能跑通
2. 90% 以上文件结构不乱
3. 可以通过 `doc_id` 回溯到原文件

## 5.2 模块 B：知识构建模块

### 目标

把解析结果构造成可检索知识单元。

### 输入

1. `parsed_docs.jsonl`
2. `parsed_tables.jsonl`

### 输出

1. `clause_chunks.jsonl`
2. `table_chunks.jsonl`
3. `bm25_corpus.jsonl`
4. `faiss_index`
5. `metadata.db`

### 要做的事

1. 对制度文档按条款切分
2. 对表格按逻辑区域切分
3. 给每个 chunk 挂元数据
4. 生成检索文本
5. 生成 embedding
6. 建 BM25 与 FAISS 索引

### 技术重点

每个 chunk 必须带这些字段：

1. `chunk_id`
2. `doc_id`
3. `title`
4. `file_type`
5. `section_path`
6. `clause_no`
7. `sheet_name`
8. `table_name`
9. `metric_name`
10. `period`
11. `source_url`
12. `local_path`

### 完成标准

1. 任意一条知识都能定位原文
2. 条款和表格能分开检索
3. 支持按文号、主题、时间过滤

## 5.3 模块 C：问题分类与查询理解模块

### 目标

把用户问题路由到正确检索链路。

### 输入

1. 用户问题

### 输出

1. 问题类型
2. 查询关键词
3. 条件过滤项
4. 是否需要多跳推理

### 要做的事

1. 建一个五分类器
2. 抽取关键词
3. 抽取条款号、文号、机构名、时间维度、指标名
4. 生成检索策略

### 建议做法

第一版优先规则 + LLM 辅助，不用一开始训练分类模型。

例如：

1. 出现“第几条/文号/规定”优先制度检索
2. 出现“报表/指标/余额/季度/月度”优先表格检索
3. 同时出现“是否符合/是否可以/是否允许”标记为场景判断题

## 5.4 模块 D：混合检索模块

### 目标

返回最小充分证据，而不是一堆相关文本。

### 输入

1. 查询理解结果
2. 索引库

### 输出

1. 候选证据列表
2. 重排后的证据包

### 要做的事

1. BM25 召回
2. 向量召回
3. 元数据过滤
4. 合并候选
5. rerank 重排
6. 选 top-k 作为证据包

### 推荐检索流程

```text
query
 -> query parse
 -> bm25 top20
 -> vector top20
 -> metadata filter
 -> merge dedup
 -> rerank top8
 -> evidence pack top3-5
```

### 完成标准

1. Top-3 证据命中率达到 90% 左右
2. 条款题能稳定命中正确条款
3. 表格题能稳定命中正确表/单元区域

## 5.5 模块 E：生成与可信校验模块

### 目标

让系统“有依据地回答”，并在不确定时拒答。

### 输入

1. 用户问题
2. 证据包

### 输出

1. 最终答案
2. 证据引用
3. 风险提示
4. 拒答结果

### 要做的事

1. 构造证据约束 prompt
2. 生成结构化回答
3. 校验数字、日期、机构名、文号
4. 校验规范强度词
5. 证据不足时拒答或要求澄清

### 回答结构固定为

1. 结论
2. 依据
3. 来源
4. 风险提示
5. 置信度

### 完成标准

1. 不允许无证据裸答
2. 所有演示问题都要带出处
3. 库外问题要能拒答

## 5.6 模块 F：前端展示模块

### 目标

把“可信”展示出来，而不是只显示答案。

### 页面至少要有 4 个区域

1. 用户问题输入框
2. 最终答案卡片
3. 证据列表卡片
4. 原文定位预览区

### 额外建议显示

1. 问题类型
2. 检索到的文件标题
3. 命中的条款编号/表格位置
4. 是否触发拒答

### 完成标准

1. 评委一眼能看懂“不是瞎答”
2. 可以点击证据看原文位置
3. 能演示一个跨文件场景

## 5.7 模块 G：评测与报告模块

### 目标

让作品从“Demo”升级为“有实验支撑的方案”。

### 输入

1. 题面 42 条种子样本
2. 扩充评测集

### 输出

1. `eval_results.json`
2. `metrics_summary.csv`
3. `ablation_report.md`
4. `error_analysis.md`

### 要做的事

1. 构造评测集
2. 定义评分规则
3. 跑完整模型
4. 跑消融实验
5. 输出图表和结论

### 必做对比实验

1. 只用 BM25
2. 只用向量检索
3. BM25 + 向量
4. 完整方案

### 完成标准

1. 指标有提升曲线
2. 能证明完整方案有效
3. 能给出错因分析

## 9. 关键接口怎么约定

为防止大家最后合不起来，一开始就约定接口。

## 9.1 解析输出接口

每条制度 chunk 至少长这样：

```json
{
  "chunk_id": "doc001_clause_003",
  "doc_id": "doc001",
  "title": "商业银行资本管理办法",
  "section_path": "第二章-第一节",
  "clause_no": "第三条",
  "text": "......",
  "source_url": "......",
  "local_path": "......"
}
```

每条表格 chunk 至少长这样：

```json
{
  "chunk_id": "doc088_sheet2_table1_r12c4",
  "doc_id": "doc088",
  "sheet_name": "表1",
  "table_name": "资本充足率统计表",
  "metric_name": "核心一级资本充足率",
  "period": "2024Q2",
  "value": "10.85%",
  "unit": "%",
  "context_text": "......",
  "source_url": "......",
  "local_path": "......"
}
```

## 9.2 检索接口

```json
{
  "query": "......",
  "question_type": "threshold",
  "filters": {
    "doc_title": null,
    "period": null
  }
}
```

返回：

```json
{
  "evidences": [
    {
      "chunk_id": "......",
      "score": 0.93,
      "text": "......"
    }
  ]
}
```

## 9.3 问答接口

输入：

```json
{
  "question": "......"
}
```

输出：

```json
{
  "answer": "......",
  "question_type": "fact",
  "evidences": [],
  "risk_note": "......",
  "confidence": 0.92,
  "refused": false
}
```

## 11. 你们最容易踩的坑

1. 一开始就做大模型 fancy 能力，结果解析和检索不稳
2. Excel 只抽文字，不保留结构
3. 不做拒答机制
4. 不做消融实验
5. 每个人自己写自己的，最后接口对不上

所以真正的优先级应该是：

1. 先把解析做稳
2. 再把检索做准
3. 再把生成做规范
4. 最后把展示做漂亮

## 12. 最后的成品应该长什么样

你们最后合并出来的作品，最理想是一个名字明确、结构清楚的系统：

### 系统名

`RegTrust-RAG`

### 对评委的呈现方式

1. 一句话介绍
   面向银行监管制度与统计报表的可信问答系统。

2. 一个页面展示
   问题、答案、证据、原文定位、拒答、置信度全在一个页面。

3. 一组指标
   准确率、证据命中率、拒答率、关键字段错误率、时延。

4. 一组对比实验
   证明混合检索和可信机制有效。

5. 一套可复现代码
   可跑、可测、可讲。

## 13. 最直接的结论

如果你们现在就要开工，我建议按下面这个执行口令来：

1. 1号先做文档解析和统一 schema
2. 2号同步做 chunk 设计和混合检索
3. 3号定义问答输出结构和校验规则
4. 4号先把前端壳子和 API 壳子搭起来
5. 5号从第一天开始整理评测集和报告模板

等解析结果一出来，检索接上；  
等检索稳定，生成接上；  
等生成接上，前端展示和评测同步收口；  
最后统一合并成一个“可演示 + 可评测 + 可答辩”的完整系统。

这才是这道题真正的执行方案。
